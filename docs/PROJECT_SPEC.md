# Quant Publisher 프로젝트 사양서

## 1. 프로젝트 개요

Quant Publisher는 개인이 Mac mini 한 대에서 운영하는 소형 퀀트 데이터 및 퍼블리싱 시스템이다.

핵심 흐름은 다음과 같다.

```text
외부 데이터
  ↓
Python 수집
  ↓
SQLite
  ↓
분석 / 백테스트
  ↓
Markdown 리포트
  ↓
Hugo
  ↓
HTML
  ↓
GitHub Pages
  ↓
Cloudflare
```

이 프로젝트의 목적은 거대한 투자 플랫폼을 만드는 것이 아니다. 작은 시스템을 먼저 완성하고 안정적으로 운영한 뒤, 실제 필요가 생길 때만 확장한다.

## 2. 프로젝트 철학

- 단순성을 우선한다.
- 실행 가능성을 우선한다.
- 데이터의 정확성과 재현성을 우선한다.
- 자동화는 사람이 반복하는 작업부터 적용한다.
- 확장성은 미래의 가능성으로만 고려하고 현재 구현을 복잡하게 만들지 않는다.
- 하나의 Mac mini에서 전체 데이터 파이프라인을 이해하고 통제할 수 있어야 한다.

## 3. 목표

### 필수 목표

- Mac mini에서 Python 프로젝트 실행
- SQLite 데이터베이스 구축
- 국내 주식 기본 종목 데이터 수집
- 재무 데이터 수집을 위한 구조 마련
- 기본 투자 지표 계산
- Markdown 리포트 자동 생성
- Hugo 정적 사이트 생성
- GitHub Pages 배포
- 기본 자동화
- 테스트와 로그를 통한 안정성 확보

### 선택 목표

- 미국 주식 데이터 추가
- 백테스트 모듈
- 월간 리포트
- 종목별 페이지 자동 생성
- 차트 이미지 자동 생성
- 검색 기능
- AI 기반 요약

선택 목표는 필수 목표가 안정화된 후에만 구현한다.

## 4. 비목표

초기 버전에서는 다음을 만들지 않는다.

- 사용자 로그인
- 회원가입
- 댓글
- 결제
- 실시간 매매 시스템
- 주문 실행
- REST API 서버
- 모바일 앱
- PostgreSQL
- Redis
- Kubernetes
- 마이크로서비스
- 복잡한 프론트엔드 SPA
- 다중 사용자 권한 시스템

## 5. 개발 환경

- OS: macOS
- 장비: Mac mini
- 언어: Python
- Python 패키지 관리: uv
- DB: SQLite3
- 분석: pandas 중심, 필요 시 numpy/polars
- 테스트: pytest
- 정적 사이트: Hugo
- 버전 관리: Git
- 배포: GitHub Pages
- DNS/CDN: Cloudflare
- 로컬 자동화: macOS launchd

특정 버전은 프로젝트 시작 시점의 안정적인 버전을 사용하고, 임의로 최신 버전 업그레이드를 강제하지 않는다.

## 6. 핵심 사용자

단일 사용자. 프로젝트 소유자가 자신의 투자 데이터와 분석 결과를 관리하고 일부 결과를 웹사이트로 공개한다.

## 7. 데이터 원칙

### 원천 데이터

원천 데이터는 외부 제공처에서 수집한다.

예:
- KRX
- Open DART
- 한국투자증권 API
- 미국 시장 데이터 제공처

실제 공급처와 API 사용 조건은 구현 시 확인한다.

### 저장 원칙

- 원천 데이터와 가공 데이터의 성격을 구분한다.
- 날짜와 종목코드를 명확하게 저장한다.
- 동일 데이터를 반복 수집해 중복시키지 않는다.
- 가능한 경우 upsert 또는 idempotent 방식으로 업데이트한다.
- 원천 데이터의 기준일과 수집 시점을 구분한다.

## 8. 리포트 원칙

리포트는 SQLite에서 직접 HTML을 만드는 방식이 아니라 다음 순서를 사용한다.

```text
SQLite
→ Python 분석
→ Markdown
→ Hugo
→ HTML
```

이렇게 하면 데이터 로직과 표현 계층이 분리된다.

## 9. 웹사이트 초기 구조

```text
/
├── Home
├── Market
├── Stocks
├── Strategy
├── Backtest
├── Reports
└── About
```

초기에는 실제 콘텐츠가 있는 메뉴만 노출한다.

## 10. 성공 기준

다음 흐름이 Mac mini에서 처음부터 끝까지 재현되면 MVP 완료다.

```text
데이터 1개 이상 수집
→ SQLite 저장
→ 분석값 계산
→ Markdown 생성
→ Hugo 빌드
→ 생성된 HTML 확인
→ Git commit
→ GitHub Pages 배포
```

## 11. 품질 기준

- 실패를 숨기지 않는다.
- API 실패 시 로그가 남는다.
- 데이터가 비어 있을 때 조용히 잘못된 값을 만들지 않는다.
- 테스트가 없는 핵심 로직은 완료로 간주하지 않는다.
- 날짜와 숫자 처리에서 암묵적 변환을 최소화한다.
- 재실행해도 데이터가 불필요하게 중복되지 않아야 한다.

## 12. 확장 원칙

향후 데이터가 커지더라도 먼저 SQLite의 한계를 측정한다.
실제 병목이 발생하기 전에는 PostgreSQL 등으로 이전하지 않는다.

향후 웹 기능이 복잡해지더라도 먼저 Hugo와 정적 JavaScript로 해결할 수 있는지 검토한다.

## 13. 완료 정의

MVP는 다음 조건을 만족할 때 완료한다.

- 프로젝트 설치 문서가 존재한다.
- 로컬에서 전체 파이프라인을 실행할 수 있다.
- 테스트가 통과한다.
- 샘플 종목 페이지가 생성된다.
- Hugo 사이트가 정상 빌드된다.
- GitHub Pages에서 페이지를 확인할 수 있다.
- 자동 실행 방법이 문서화되어 있다.
